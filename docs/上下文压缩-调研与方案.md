# ember 上下文压缩：调研 + 可落地方案

> 结论：**不发明新机制**。学 Codex 的"重建历史"骨架、OpenHands 的"原子边界 + 压到一半"、LangMem 的"摘要滚动扩展"，落到 ember 现有的 3 个函数里，约 150 行。

---

## 1. 别人怎么做的

### 1.1 Codex CLI（`codex-rs/core/src/compact.rs`）

- **触发**：自动（窗口用量）+ 手动 `/compact`。
- **做法不是"删几条"，而是重建整段历史**：
  1. 把当前历史交给模型，让它输出一份摘要；
  2. 新建历史 = `初始上下文（base instructions）` + `最近若干条用户消息` + `一条摘要项`。
- **两个细节特别值得抄**：
  - 摘要项以固定前缀开头（`SUMMARY_PREFIX`），压缩时**识别并忽略旧摘要**，天然避免"摘要套摘要"；
  - 保留的用户消息有 token 预算（`COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000`），从新往旧挑，挑不下的就地截断。
- 压缩过程中若仍超窗：从最旧逐条丢再重试（保住 cache 前缀）。

### 1.2 OpenHands（`context/condenser/llm_summarizing_condenser.py`）

- **三种触发**：显式请求 / token 超限 / 事件数超限；**token 超限算硬要求**，事件数只是软要求。
- **参数即策略**：`max_size`（事件数上限，标准 agent 用 80）、`keep_first`（开头永不压缩，用 4）、`minimum_progress=0.1`（一次至少压掉 10%，否则算失败，防止"压了等于没压"）。
- **压到一半，不是压到刚好**：目标 `max_size // 2`（滞回，避免刚压完立刻又触发）。
- **按"原子单元"切边界**（`manipulation_indices`）：绝不把一个工具调用和它的结果切开 —— 这正是我们自己会踩的 400 坑。
- **兜底 `hard_context_reset`**：要压的内容本身太大、摘要调用失败时，把每条事件截断到 0.8 倍重试，最多 5 次。
- 摘要位置：**在被删区间的原位插入**，不是追加到末尾。

### 1.3 LangGraph / LangMem（`SummarizationNode`）

- 触发看 `max_tokens_before_summary`，摘要长度封顶 `max_summary_tokens`。
- 维护一个 `RunningSummary`：**旧摘要 + 新消息 → 新摘要**（就地扩展，只有一份），原文只保留最后 N 条。

### 1.4 三家共同点（= 可直接复用的四条）

1. 触发按 **token/字符预算**，不按消息条数（我们现在的 `max_history=60` 就是反例）。
2. 摘要是**单独一次调用**：system 放规则，user 放待压内容，不挂工具。
3. 永远保留两类东西：**开头固定项**（system、首个任务）和**最近一轮原文**。
4. 切点必须对齐"**消息组**"，摘要**就地替换**，且只有一份（滚动更新，不叠加）。

## 2. ember 落地设计

### 2.1 数据形状（摘要就地占位，会话文件仍是唯一真源）

会话文件保持 JSONL，新增一种记录：

```json
{"role":"user","content":"..."}
{"role":"assistant","tool_calls":[...]}
{"role":"tool","tool_call_id":"...","content":"..."}
{"role":"__summary__","content":"【早前对话摘要】..."}
```

- `__summary__` **就放在它替换掉的那段内容原来的位置**（对应 OpenHands 的 `summary_offset`、Codex 的摘要项）——不需要 `upto` 之类的偏移量，文件顺序本身就是真相。
- 载入时把它复原成一条普通 user 消息（前缀 `【早前对话摘要】`），位置是历史第 2 条（紧跟 system）。**永远只有一条**：再压时是"旧摘要 + 新内容 → 新摘要"。
- 压缩时整文件**原子重写**（先写 `.tmp` 再 `os.replace`），不会出现"重写一半被杀导致会话损坏"。
- 被折叠的原文追加到 `<会话名>.archive.jsonl`，摘要末尾留一行指针，agent 用现有 `search_text` 就能回捞。
- 平时仍是 v1.6 的逐条 append，所以"关窗口不丢记录"不受影响。

### 2.2 触发与预算

| 配置项 | 默认 | 说明 |
|---|---|---|
| `context_budget` | 120000 | 上下文字符预算（≈60k token，按 v4-flash 窗口保守取；`0` = 关闭压缩） |
| `context_keep_tail` | 6 | 尾部保留多少个"消息组"原文 |
| `context_keep_first` | 1 | 除 system 外，开头保留几条（首个任务） |
| `context_archive` | on | 被折叠的原文是否另存 `.archive.jsonl`（可回捞） |

- 估算用**字符**而非真 token（stdlib 无 tokenizer；中文 1 字≈1 token，英文 4 字符≈1 token，字符数偏保守，不会低估）。
- 水位 = `context_budget * 0.75` 触发；压到 `context_budget * 0.5` 为止（学 OpenHands 的滞回）。
- 检查时机：**每轮开始前**（`run_turn` 入口），而不是等 API 报 400。

### 2.3 切分：只在"消息组"边界下刀

```
组 = 一条 user
   | 一条 assistant（无 tool_calls）
   | 一条 assistant(tool_calls) + 它声明的全部 tool 结果
```

- 可压区间 = 第 `context_keep_first` 组之后、倒数 `context_keep_tail` 组之前。
- 若可压区间为空（一问一答还没几轮）→ 跳过，不动。
- **绝不**出现"assistant 留一半、tool 被切走"的历史 —— 这是唯一会让下一轮 400 的切法。

### 2.4 摘要调用

- 一次**非流式**请求，不带工具，`max_tokens ≈ 1200`。
- system（固定模板，约 200 字）：

```
你在压缩一段 agent 与用户的对话记录。只输出摘要，不要寒暄。
必须保留：
1) 用户目标与约束（原话中明确说过的）
2) 已做出的决定/结论
3) 改动过或创造过的文件路径
4) 尚未完成的事、下一步
5) 用户偏好（语言、风格、忌讳）
6) 关键事实（环境、账号无关的配置、报错原文要点）
丢弃：寒暄、重复的试错过程、已被推翻的方案。
长度 ≤ 800 字，用中文，条目式。
输入末尾若有【已有摘要】，把它合并进新摘要（不是并列两份）。
```

- user：`【已有摘要】…`（若有）+ `【待压缩对话】`（每组渲染成一行，单组超 1200 字则截断，总长 4 万字符封顶）。
- 输出写成一条**就地的** `__summary__` 记录（位置在保留头部之后、保留尾部之前）。
- **失败处理**：捕获所有异常 → 降级为"按组直接丢弃 + 一行说明"，本轮照跑，绝不阻塞。

### 2.5 与现有代码的接入点（改动很小）

| 位置 | 改动 |
|---|---|
| `load_session` | `__summary__` 记录就地复原成摘要消息 |
| `save_session` / `append_message` | 摘要消息写回成 `__summary__`；重写走 `.tmp` → `os.replace` 原子替换 |
| `run_turn` 入口 | `maybe_compact()`：算预算 → 切组 → 调摘要 → 就地改 history + 重写文件 |
| `trim_history` | 降级为"最后兜底"，且**永不裁摘要**（否则等于把记忆本身删了） |
| `api_stream` | 不变（history 本身就是消息列表） |
| 命令 | `/compact`（立刻压一次）、`/context`（字符数/预算/摘要长度） |
| 配置 | `context_budget` / `context_keep_tail` / `context_keep_first` / `context_archive` |

实际实现（v1.7）与本文的差异只有两处：
1. 不需要 `upto` 偏移量 —— 摘要就地占位，重载时按文件顺序复原；
2. 额外加了一条护栏：一次只折叠 1 条消息时不压（除非手动 `/compact`），避免把一问一答拆成两半。

伪代码：

```python
def maybe_compact(history, model, session_path):
    if not CONTEXT_BUDGET or estimate(history) <= CONTEXT_BUDGET * 0.75: return
    groups = group_messages(history[1:])          # tool 组不拆开
    cut = len(groups) - keep_tail
    while cut < len(groups) - 1 and size_from(cut) > CONTEXT_BUDGET * 0.5:
        cut += 1                                   # 压到"一半"为止
    mid, tail = groups[keep_first:cut], groups[cut:]
    if len(mid) < 2: return
    summary = summarize(prev_summary, mid)         # 失败 -> 降级丢弃
    append_archive(session_path, flatten(mid))
    history[:] = [system, summary_msg(summary)] + flatten(groups[:keep_first] + tail)
    save_session(session_path, history)            # 原子重写
```

### 2.6 这一步明确不做

- **RAG / 向量库**：要额外依赖和一次索引，`__summary__` + 现有 `search_text` 已经能做"按需回捞"（存档文件就在 `sessions\` 里）。
- **子代理隔离**：要改架构，与"单文件"冲突；以后想要，等价物是"把长探索丢给一次性的 -p 调用，只回结论"。
- **prompt cache**：压缩会改前缀，两者互相打架；等压缩频率稳定后再看。

## 3. 实施顺序

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1** ✅ | `__summary__` 记录 + 组切分 + 摘要调用 + 触发水位 + `/compact` `/context` + archive | 自检 98 项全过（含压缩后无孤儿 tool、落盘可重载、裁剪不裁摘要）；真实 API 端到端：第 4 轮触发压缩，摘要记住“ZETA-42”并在压缩后正确答出 |
| **P2** | 长会话压测（200 轮）、摘要质量回归（对比"压前/压后同一问题"） | 长会话跑 200 轮不炸 |
| **P3** | `memory.md`（常驻事实，不参与压缩）+ 工具结果去重 | 用户说"记住 X"后，隔 50 轮仍记得 |
